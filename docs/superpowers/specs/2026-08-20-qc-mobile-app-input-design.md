# 质检移动端（App）录入设计文档

- 日期：2026-08-20
- 状态：设计待评审
- 范围：移动端 App（uni-app）质检录入；后端判定引擎与 PC 端不变
- 前置文档：`docs/superpowers/specs/2026-08-16-mes-qc-quality-inspection-design.md`（QC 模块整体设计，已实施）

## 1. 背景与目标

QC 模块已在后端与 PC 前端实施完毕：四类检验单（IQC/IPQC/OQC/RQC）、检测项模板、判定引擎、缺陷记录、下游放行拦截均已就绪。但移动端 App（`app/pages/mes/`）目前只有 pro/pur/wm 三个域，**完全没有质检页面**：

- 采购到货登记（`app/pages/mes/pur/receipt.vue`）提交后会自动生成 IQC，但提示"请在 PC 端完成质检并确认入库"；
- 收货历史只能只读显示一个检验状态标签；
- 检验员实际作业链路是"现场量测 → 回办公室 PC 录入 → 判定"，存在现场断点。

本设计目标：在 App 端提供质检现场录入与判定能力，消除该断点。第一期聚焦现场属性最强的两类检验。

### 1.1 关键产品决策（用户已确认）

| 决策 | 结论 |
|------|------|
| 第一期范围 | **IPQC + IQC**；OQC/RQC 后置 |
| App 能否建单 | 支持扫码**手工建 IPQC**（首检/巡检/抽检）；IQC 仅处理自动生成的待检单，不开放手工建 |
| 判定与让步 | App 端完成录入 + 判定 + 让步接收全流程；让步由检验员填理由即生效，与 PC 一致，无需主管审批 |
| 离线能力 | **纯在线**，不做本地草稿/离线架构；网络异常时保留页面内存数据供重试 |
| 待检入口 | **待检列表 + 扫码双通道**；列表按 IPQC/IQC 分 Tab |
| 待检单归属 | **共享待检池**，所有检验员可见，首次暂存即认领（PENDING→INSPECTING），判定时回填检验员 |
| 图片存储 | 拍照后直接上传 MinIO，与 App 现有拍照能力一致 |
| 判定逻辑归属 | 仍由后端 `QcJudgeService` 统一执行，App 只做前端视觉预判（不拦截），保证口径唯一 |
| 作废/基础数据维护 | 检验单作废、检验模板/检测项/缺陷字典/判定配置维护全部留在 PC |

## 2. 页面结构与导航

新增 `app/pages/mes/qc/` 目录，共 5 个页面；在工作台 `app/pages/work/index.vue` 增加"质检"入口。

```
工作台 → 质检首页（待检列表）
              ├── 右上角：扫码图标、历史入口（时钟图标）
              ├── [IPQC Tab] / [IQC Tab]
              ├── 检验单卡片列表（点击进入录入页）
              └── [IPQC Tab 底部] 手工建单按钮

手工建 IPQC 页（scan-create）
  扫流转卡/工单 → 选检验类型(首检/巡检/抽检) → 自动带出模板 → 确认建单 → 进录入页

检验录入页（inspect）
  ├── 单据头信息（单号、来源、物料/工序、状态、本次检测数量）
  ├── 检测项卡片列表（逐行录实测值，含拍照）
  ├── 缺陷记录区（增删改，含拍照、等级、处置）
  ├── 底部操作栏：暂存 / 提交判定
  └── 判定结果区/页（PASS/FAIL/CONCESSION；FAIL 可填让步理由）

检验历史页（history）
  已完成单据列表（COMPLETED/CLOSED），按检验员/时间筛选，点击只读查看详情
```

### 2.1 导航要点

- 首页用两个 Tab 区分 IPQC / IQC：IPQC 卡片侧重工序/工作站，IQC 卡片侧重供应商/收货单。
- 扫码在首页右上角与手工建单页内均可触发；扫码后自动识别单据类型并路由（见 4.2）。
- "手工建单"按钮仅在 IPQC Tab 显示。
- 历史页只读，不做编辑。

## 3. 检测项录入交互（核心）

PC 端用 `el-table`，App 改为卡片流：每个检测项一张卡片。

### 3.1 检测项卡片

```
┌─────────────────────────────┐
│ ① 外观检查           [必检]  │  检测项名称 + 必检标记
│ 工具：目视  方法：GB/T 2828  │  工具/方法（灰色小字）
│ 标准值：无划痕、无变形        │  标准值快照
│ ┌─────────────────────────┐ │
│ │ 录入区（按值类型变）      │ │
│ └─────────────────────────┘ │
│ 致缺陷[0] 严缺陷[0] 轻缺陷[0]│  三个数字 stepper（默认 0）
│ 行判定：待检 / 合格 / 超差    │  提交判定后由后端回填显示
└─────────────────────────────┘
```

### 3.2 五种值类型的录入控件

| 值类型 | 控件 | 行为 |
|--------|------|------|
| NUMBER | 数字输入框 + 单位 | 下方显示标准值与上下偏差（如 `10.00 ±0.05 mm`）；失焦时前端即时预判标签：范围内"正常"（绿）、超出"超差"（红）。预判仅视觉提示，不拦截、不作为最终判定 |
| COUNT | 整数输入框 | 计数型（如疵点数），可带标准范围预判 |
| DICT | 按钮单选组 | 如"合格 / 不合格"，横向排列，点选高亮 |
| TEXT | 多行文本框 | 最多 500 字 |
| FILE | 拍照/相册上传 | 调 `uni.chooseImage`，支持多张，缩略图可预览/删除；上传 MinIO，URL 写入 `checkValText`，与 PC 端字段格式保持一致（多 URL 以逗号分隔） |

### 3.3 缺陷记录区

检测项卡片下方是独立的"缺陷记录"区块（与 PC 端 `QcDefectRecord` 独立子表对应，一条缺陷可跨多个检测项）：

```
── 缺陷记录 ─────────────  [+ 添加缺陷]
  ┌───────────────────────────┐
  │ 缺陷：划痕  等级：[严重 ▼]  │
  │ 数量：[3]  处置：[返工 ▼]   │
  │ 📷 📷 （2张）      [删除]   │
  └───────────────────────────┘
```

- 缺陷编码从 `QcDefect` 字典拉取下拉；
- 等级三选一：致命（CRITICAL）/ 严重（MAJOR）/ 轻微（MINOR）；
- 处置方式走现有字典（返工/报废/让步/返修等）；
- 照片走 MinIO，可多张；支持多条新增、删除。

### 3.4 录入防错

- 必检项未填：提交时逐项检查，未填卡片标红并自动滚动到第一个未填项；
- 数字超差：失焦即时提示但不拦截（允许录异常值，最终由后端判定）；
- NUMBER/COUNT：键盘拦截非数字与负数；
- 已判定行锁定：COMPLETED 状态下所有控件置灰，不可编辑（与 PC 一致）；
- 本次检测数量：单据头必填，抽检量从模板带出可改，作为缺陷率分母，必须 > 0 才能提交判定。

## 4. 数据流与接口

### 4.1 页面与后端接口映射

新增 `app/api/mes/qc/` 目录，复用后端已有端点，**后端零改动**（唯一可能的增量见 4.2 说明）：

| App 页面/动作 | 方法 | 后端端点 | 说明 |
|---------------|------|----------|------|
| 待检列表（IPQC） | GET | `/mes/qc/ipqc/list` | 传 `status=PENDING,INSPECTING`，分页 |
| 待检列表（IQC） | GET | `/mes/qc/iqc/list` | 同上 |
| 检验单详情（含行+缺陷） | GET | `/mes/qc/ipqc/getInfo/{id}` 或 `/iqc/getInfo/{id}` | 返回 `info` + `lines` + `defectRecords` |
| 暂存（保存录入） | PUT | `/mes/qc/ipqc/edit` 或 `/iqc/edit` | 传整单：头 + lines + defectRecords，状态保持/推进至 INSPECTING |
| 手工建 IPQC | POST | `/mes/qc/ipqc` | 传工单/流转卡/工序/检验类型，后端按模板生成行 |
| 提交判定 | PUT | `/mes/qc/ipqc/judge` 或 `/iqc/judge` | body 含整单数据 + `concessionReason`（让步时填） |
| 历史列表 | GET | `/mes/qc/ipqc/list`、`/iqc/list` | 传 `status=COMPLETED,CLOSED` |
| 缺陷字典 | GET | `/mes/qc/defect/list` | 建缺陷记录时下拉 |
| 图片上传 | POST | 现有通用上传接口 | MinIO，返回 URL |

`judge` 端点与 PC 完全共用：App 把整单（含最新 lines、defectRecords、concessionReason）一次性 PUT，后端先持久化再执行判定引擎，返回判定结果（PASS/FAIL/CONCESSION + 每行行判定 + 三档缺陷统计）。App 不复制任何判定规则。

### 4.2 扫码路由逻辑

扫码结果字符串按以下分支处理：

1. 流转卡号/工单号 → 复用现有扫码解析（参考 `app/api/mes/pro/procard.js` 的 `getCardScanResult`）：
   - 该卡/工单已有进行中 IPQC → 直接进录入页；
   - 无 → 跳手工建 IPQC 页并自动带值。
2. 收货单号（item recpt code）→ 按单号查收货单及其 IQC：
   - 已有 IQC → 进录入页；
   - 无 → 提示"该收货单未生成检验单或已免检"。
   - **后端增量待确认**：若现有无"按收货单号查 IQC"的轻量端点，需新增一个（仅查询，不动判定逻辑）。实现计划阶段核实并补。
3. 检验单号自身 → 直接进对应录入页。
4. 无法识别 → 提示"无效的质检二维码"。

### 4.3 状态流转与并发

```
PENDING ──首次暂存（认领）──> INSPECTING ──提交判定──> COMPLETED(PASS/FAIL/CONCESSION)
                               │                         │
                               └────可继续编辑────────────┘（判定前）
COMPLETED 后全部只读
CLOSED（作废）仅 PC 端操作
```

- **首次暂存即认领**：检验员打开 PENDING 单时不改变状态（避免浏览即锁定）；首次调 `edit` 暂存录入数据时，后端将状态推进到 INSPECTING，以此视为认领，避免两人长期同时编辑同一单。
- **乐观锁**：`edit`/`judge` 带版本校验；若返回"单据已被他人处理"，弹窗提示"该检验单已由 {检验员} 处理"并刷新详情/返回列表。后端是否已有版本控制在实现计划阶段核实，若无则评估新增（共享待检池场景的必要保护）。

## 5. 异常处理

| 场景 | 处理 |
|------|------|
| 网络中断 | 弹"网络异常，请检查连接后重试"，保留页面内存已填数据不清除，用户重试；图片单张失败可重试，不阻断其他录入 |
| 单据已被他人认领/判定 | 提示"该检验单已由 {检验员} 处理"，确认后刷新详情/返回列表，防覆盖 |
| 必检项未填 | 拦截提交，未填卡片标红，顶部提示"还有 N 项未填写"，自动滚动到第一个未填项 |
| 本次检测数量未填或为 0 | 拦截提交；数量大于来源单数量给软提醒（允许加严抽检） |
| 图片上传中提交 | 按钮置灰显示"图片上传中…"，全部上传完成才允许提交 |
| 让步理由未填 | FAIL 选"让步接收"时理由必填，空则拦截 |
| 模板无检测项 | 建单/打开时若 lines 为空，提示"未配置检测项，请在 PC 维护模板"，不允许空单提交判定 |
| 登录失效（401） | 跳登录页，登录后回到原页面（内存数据可能丢失，纯在线可接受） |
| 重复提交判定 | 按钮点击后置灰加 loading，直到返回结果 |
| 后端判定 FAIL | 正常展示结果页（红色不合格），提供"填让步理由"和"返回列表"；不合格单由 `QcGateService` 在下游业务自动拦截，App 不额外处理 |

## 6. 测试策略

遵循项目 `run-tests` 约定，三层验证；App 交互必须真机/浏览器实测，不以 curl 代替。

### 6.1 后端
- 复用接口在移动端参数下行为正确；
- 若新增"按收货单号查 IQC"端点，补单测/接口测试；
- 判定逻辑已由 `QcJudgeService` 覆盖，不重复测，只验证 App 提交的整单能被正确判定。

### 6.2 前端（App）
- 五种值类型控件单测：NUMBER 超差预判、DICT 单选、FILE 多图上传/删除；
- 缺陷记录增删、必检项校验逻辑；
- 接口联调：字段命名前后端一致（camelCase），重点 `checkValText`、`defectRecords`、`concessionReason`。

### 6.3 端到端真机验证（必做）
1. **IPQC 手工建单全流程**：登录 App → 扫流转卡 → 选巡检 → 确认建单 → 逐行录五种类型检测项（含拍照上传 MinIO）→ 加缺陷带照片 → 暂存 → 重进确认回显 → 提交判定 → 看到 PASS → PC 确认单据完成、待办回写。
2. **IQC 录入与让步全流程**：PC 做一笔到货登记生成 IQC → App 扫收货单进入 → 录入 → 制造不合格（超差值/致命缺陷）→ 提交判定看到 FAIL → 填让步理由 → 确认 CONCESSION → 验证下游入库放行（让步）；再测一单 FAIL 不让步被拦截。
3. **异常场景**：两人同时打开同一待检单，一人先判定，另一人提交看到"已被他人处理"；必检项留空被拦截；断网提交看到重试提示且页面数据不丢。
4. **回归**：PC 端录入/判定功能不受影响（共用 edit/judge 接口）。

## 7. 不在本期范围

- OQC 出货检、RQC 退料检的 App 录入（第二、三期）；
- IQC 手工建单；
- 检验单作废、模板/检测项/缺陷字典/判定配置维护（PC）；
- 离线草稿/本地数据库/后台同步；
- 让步接收的主管审批流（未来如需，应在后端加审批节点，而非限制操作端）；
- 样品级结果、质量统计报表。
