# 销售出库 — 发货流程设计（PRD）

> 状态：**设计评审中** ｜ 版本：v1.0 ｜ 日期：2026-07-26
> 角色：产品经理 ｜ 适用模块：`wm/product_sales`（销售出库单）
> 设计原则：后端拥有数据逻辑，前端无感知；遵循本项目头/行/明细三层单据范式与 Redis 锁+事务模板库存扣减范式。

## 0. 文档目的与读者

本文档面向**开发评审**，定义「销售出库 — 发货」标准流程的产品方案：业务流程、页面设计、字段清单、状态机、数据模型扩展、接口契约、权限、打印。

读者在评审前请先确认：你已读过 [`领料单生命周期设计.md`](领料单生命周期设计.md) 和 [`backend/AGENTS.md`](../../backend/AGENTS.md) 的锁+事务约定，理解本项目「头/行/明细 + 状态机 + 过账扣库存」的标准范式。

## 1. 现状盘点（As-Is）

### 1.1 已具备的能力 ✅

| 能力 | 实现位置 | 评价 |
|------|----------|------|
| 销售出库单头/行/明细三层 | `qxx_wm_product_sales` / `_line` / `_detail` | ✅ 范式标准 |
| 状态机 | `WmProductSalesConstants` | ✅ `DRAFT→PARTIAL_POSTED/POSTED→SHIPPED→CLOSED`，可作废 |
| 过账扣库存（FIFO 跨批次） | `WmProductSalesServiceImpl.postOut` | ✅ Redis 锁+事务，写 `qxx_wm_transaction`+`qxx_pro_material_trace` |
| 从销售订单生成草稿 | `buildFromSaleOrder` | ✅ 按仓 FIFO 自动拆行 |
| 作废回滚（PARTIAL_POSTED） | `rollbackPostedStock` | ✅ 逐条恢复 onhand+available，写正数冲回 |
| 发货登记 | `ship()` + `index.vue` 内嵌 6 字段弹窗 | ⚠️ **过于简陋，是本次设计的重点改造对象** |

### 1.2 现状缺陷（Pain Points）❌

1. **发货弹窗塞在列表页内联**（`index.vue` L66-89），6 个字段挤在一起，**无法体现「标准发货」应有的环节划分**。
2. **缺少装箱环节**：`qxx_wm_product_sales_line` 有 `quantity_box/box_spec/box_length/width/height/volume/weight` 字段，但**前端从未采集、后端从未汇总**，头表 `total_box/total_volume/total_weight` 始终为空。
3. **无拣货/备货复核环节**：过账即出库，仓管与销售之间没有「货已备齐可发」的交接确认，出错只能事后退货。
4. **无送货单/装箱单打印**：现场出库靠手写，电子单据缺失，客户收货无据可对。
5. **发运信息单薄**：只有物流公司/单号/费用/地址/收货人/电话，**缺车牌、司机、电话、发货方式（自提/物流/快递）、承运商**等制造企业高频字段。
6. **无签收闭环**：`SHIPPED` 之后只能手动「关闭」，**没有客户签收时间、签收人、签收备注、回单管理**，无法证明交付完成（财务对账、外贸清关都需要）。
7. **过账与发货顺序耦合**：当前要求必须先 POSTED 才能发货（`isShippable` 允许 POSTED/PARTIAL_POSTED），但**部分发货场景（一张单分多次发运）不支持**——`ship()` 是一次性把单据推到 SHIPPED，第二次发运无入口。
8. **缺发运计划**：客户要求 7/30 交货，系统无「计划发货日期」字段，无法提前备货排程。

## 2. 业务流程设计（To-Be）

### 2.1 总体流程图

```
┌─────────┐    ┌──────────┐    ┌──────────┐    ┌──────────┐    ┌──────────┐    ┌──────────┐
│  草稿   │───▶│ 过账出库 │───▶│  拣货    │───▶│  装箱    │───▶│ 发运登记 │───▶│  签收    │
│ DRAFT   │    │ POSTED   │    │ PICKING  │    │ PACKING  │    │ SHIPPED  │    │ RECEIVED │
└─────────┘    └──────────┘    └──────────┘    └──────────┘    └──────────┘    └──────────┘
      │              │                                              │                  │
      │              ▼                                              ▼                  ▼
      │     PARTIAL_POSTED                                    （多次发运）          CLOSED
      │     （多次过账）                                       Shipment 子表       （单据关闭）
      ▼
   CANCELED（草稿/部分过账可作废，回滚库存）
```

### 2.2 六个环节定义

| # | 环节 | 状态 | 责任角色 | 输入 | 输出 | 是否新增 |
|---|------|------|----------|------|------|----------|
| 1 | **过账出库** | DRAFT→POSTED | 仓管 | 出库单 + 批次拣货 | 扣库存、生成出库明细 | 已有，沿用 |
| 2 | **拣货** | POSTED→PICKING | 拣货员 | 出库明细（按批次） | 拣货任务单、实物备齐 | 🆕 |
| 3 | **装箱** | PICKING→PACKING | 包装员 | 备齐货物 + 箱规 | 装箱明细、唛头、箱数/体积/重量 | 🆕（字段已存在，激活采集） |
| 4 | **发运登记** | PACKING→SHIPPED | 发货员 | 装箱结果 + 物流信息 | 物流单号、车辆/司机、运费 | 改造（扩字段 + 独立页） |
| 5 | **签收** | SHIPPED→RECEIVED | 客户/业务员 | 物流回单 | 签收时间/人/备注 | 🆕 |
| 6 | **关闭** | RECEIVED→CLOSED | 业务员 | — | 单据归档 | 沿用 |

> **设计决策**：拣货/装箱作为**可选环节**（开关控制），轻量企业可关闭，直接 POSTED→SHIPPED。这样既支持标准流程，又不破坏现有轻量用户的体验。详见 §6 配置。

### 2.3 关键业务规则

| 规则 | 说明 |
|------|------|
| **R1 过账前置** | 发货前必须过账（扣库存）。未过账单据不能发货，避免「空发」。 |
| **R2 多次发运** | 一张出库单可分多次发运（部分发货）。每次发运生成一条 `Shipment` 记录，累计 `shipped_quantity`。全部发完才转 SHIPPED 终态语义（实际状态用 PARTIAL_SHIPPED/SHIPPED 区分）。 |
| **R3 装箱与发运解耦** | 装箱在发运前完成；发运时关联已装箱的箱列表，不再编辑箱内明细。 |
| **R4 签收才可关单** | 必须签收（或业务员手动标记「视为已签收」）才能 CLOSED，杜绝「发了没收到」的单据黑洞。 |
| **R5 作废窗口** | 仅 DRAFT/PARTIAL_POSTED/PICKING 可作废；PACKING 之后（已装箱）禁止作废，只能走退货。 |
| **R6 库存一致性** | 拣货/装箱/发运**不再扣库存**（过账时已扣），仅做数量复核，避免重复扣减。 |

### 4.4 头表 `qxx_wm_product_sales` 扩展字段（增量 ALTER）

| 新字段 | 类型 | 说明 |
|--------|------|------|
| `shipped_quantity` | decimal(16,4) | 已发运量（冗余，便于列表与汇总） |
| `ship_status` | varchar(20) | 发运状态：UNSHIPPED/PARTIAL_SHIPPED/SHIPPED/RECEIVED（与 `status` 正交，避免污染主状态机） |
| `plan_ship_date` | date | 计划发货日期（来自销售订单 request_date 带入） |

> **设计决策**：`ship_status` 与头表 `status`（DRAFT/POSTED/SHIPPED/CLOSED）分离，避免「主状态机 + 发运子状态」耦合。头表 `status` 的 `SHIPPED` 语义改为「全部发运完成」，由 `shipped_quantity >= total_quantity` 自动推导。

### 4.5 状态机扩展（`WmProductSalesConstants`）

```
现有：DRAFT → PARTIAL_POSTED/POSTED → SHIPPED → CLOSED
新增：                                  PICKING → PACKING（可选环节，配置开关）
新增发运子状态（ship_status）：
        UN_SHIPPED → PARTIAL_SHIPPED → SHIPPED → RECEIVED
```

`isShippable()`（主状态可发货判定）改为：`status IN (POSTED, PICKING, PACKING, PARTIAL_SHIPPED)`，即过账后、未全部发完前都可继续发运。

## 5. 接口契约（前后端 API）

> 遵循本项目 API 契约规范：单条 `{code:200,msg,data:{}}`，列表 `{code:200,msg,rows,total}`。

### 5.1 发运单 CRUD

| 方法 | 路径 | 说明 | 权限 |
|------|------|------|------|
| GET | `/mes/wm/product_sales/shipment/list` | 发运单列表（按 salesId 过滤） | `mes:wm:sales:list` |
| GET | `/mes/wm/product_sales/shipment/{shipmentId}` | 发运单详情（含关联箱） | `mes:wm:sales:list` |
| POST | `/mes/wm/product_sales/shipment` | 新增发运（勾选箱、写物流信息、回写头表 shipped_quantity） | `mes:wm:sales:ship` |

### 5.3 打印（前端最简方案，本期定稿）

**技术选型：浏览器原生 `window.print()` + `@media print` 专用样式**，零后端工作量，现场立即可用。

**实现方式**：不新增后端打印接口，复用 §5.4 `getDetail` 返回的全量数据（头 + 行 + 装箱 + 发运记录），前端用独立的打印组件渲染 + 调浏览器打印。

| 单据 | 前端组件 | 数据来源 | 用途 |
|------|----------|----------|------|
| 送货单 | `components/print/DeliveryPrint.vue` | `getDetail`（头+行+签收栏） | 随车交接，客户签收凭证 |
| 装箱单 | `components/print/PackingPrint.vue` | `getDetail.boxes` | 每箱贴附，清点核对 |
| 发运单 | `components/print/ShipmentPrint.vue` | 单条 shipment + 关联箱 | 物流交接 |

**打印交互**：点【打印】按钮 → 新开路由页 `/product_sales/print/:salesId?type=delivery`（纯打印视图，无导航） → `onMounted` 自动 `window.print()` → 用户选打印机/另存 PDF。

**样式约束**（写进组件 `<style media="print">`）：
- A4 纸张尺寸（`@page { size: A4; margin: 12mm }`）
- 表格避免跨页断裂（`tr { page-break-inside: avoid }`）
- 隐藏所有操作按钮/导航（`@media print { .no-print { display:none } }`）
- 签收栏固定底部（客户签字、日期、盖章区）

> **本期不做**：后端 PDF 生成（Jasper/Wkhtmltopdf）、打印模板在线设计器、批量打印。若将来客户要求精美 PDF 或归档，再引入后端方案，届时前端组件数据结构可平滑迁移。

## 8. 关键技术约束（开发必须遵守）

1. **库存扣减只发生在过账环节**，拣货/装箱/发运/签收都不扣库存（R6）。避免重复扣减 bug。
2. **发运、装箱写表必须加 Redis 锁**，key=`wm:salesout:lock:{salesId}`，**先锁后事务**（`TransactionTemplate`），禁止在加锁方法上加 `@Transactional`。（见 `backend/AGENTS.md` 锁标准用法）
3. **所有 SQL WHERE 带 `factory_id`**（`<if>` 条件，拦截器注入值）。
4. **Flyway INSERT 显式写 factory_id**（裸 JDBC 不走拦截器）；业务 INSERT 不写（拦截器注入）。
5. **后端负责所有数据计算与聚合**：箱数/体积/重量汇总、shipped_quantity 回写、ship_status 推导，都由后端做，前端只展示。
6. **打印本期走前端**（`window.print()` + `@media print`），不新增后端打印接口；数据复用 `getDetail` 全量返回，前端独立打印组件渲染。将来转后端 PDF 时数据结构可平滑迁移。
7. **附件回单上传走 MinIO**（项目已有），返回 URL 存 `attachment_url`。
8. **多次发运的并发安全**：同一出库单并发新增发运时，`shipped_quantity` 累加必须在锁内 SELECT-then-UPDATE，避免丢失更新。
