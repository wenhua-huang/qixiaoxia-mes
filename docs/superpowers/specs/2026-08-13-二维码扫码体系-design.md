# 二维码生成与扫码体系设计

> **状态**：设计草案，待评审
> **日期**：2026-08-13
> **作者**：产品设计（ZCode）
> **范围**：MES 生产（流转卡 / 报工）+ 仓储（物料 / 卷料 / 入库）全链路二维码生成与扫码方案，分三期交付

---

## 1. 背景与现状

### 1.1 现状盘点（调研结论）

| 能力 | 现状 | 证据 |
|------|------|------|
| 二维码/条码**生成** | ❌ 完全空白 | 全代码库无 ZXing / qrcode / jsbarcode 任何依赖，无任何码图渲染代码 |
| **扫码** | ⚠️ 仅 App | App 用 `uni.scanCode`（8 个页面）；PC 前端零扫码能力 |
| 码数据模型 | 🟡 半成品 | `qxx_wm_barcode` 表是"文本登记簿"（手敲内容、无图、无打印）；`ProCard.barcode_url` 字段**声明了但连 Flyway 迁移都没有**、后端从不填值 |
| 流转卡实体 | ✅ 完整 | `qxx_pro_card`：工单开工自动建卡、可拆卡、有 `card_code`(CRD+日期+序号)、`current_process_id`（实时工序游标）、`status`(ACTIVE/OUTSOURCING/COMPLETED/SCRAPPED) |

### 1.2 核心问题

**报工从不扫流转卡。** 现状工人扫码扫的是**工单码**，流转卡由后端 `ProFeedbackServiceImpl.resolveActiveCardId()` 偷偷自动取"工单第一张 ACTIVE 卡"。

这带来两个问题：
1. **歧义隐患**：一个工单可能有多张卡（拆批），自动取"第一张"可能取错。
2. **报工步骤冗长**：App 报工要 4 步（扫工单码 → 选工序任务 → 填数量 → 填参数），而流转卡自带工序游标 `current_process_id`，本可直接定位。

### 1.3 设计目标

1. **以流转卡码作为生产侧统一扫码锚点**——一卡一批、自带工序游标，扫一下系统就知道报哪道工序。
2. **建立统一码体系**：一个扫码入口（App），按码类型自动分发到不同业务，前端零判断。
3. **后端拥有数据逻辑**：扫码反查上下文全由后端封装，前端零拼接（遵循项目 AGENTS.md 职责划分）。
4. **打印机无关、零硬件门槛落地**：一期用现有 A4 打印，标签打印机可后续插拔接入。
5. **数据库零迁移**：复用已有 `card_code` / `batch_code` / `roll_code`，payload 全部派生。

## 2. 设计原则

| 原则 | 说明 |
|------|------|
| **码 = 业务编码的二维码化** | 不发明新标识。流转卡码就是 `card_code` 的二维码，物料码就是 `batch_code` 的二维码。扫码坏了工人能读出码手输。 |
| **payload 带类型前缀** | `QXX\|TYPE\|CODE`，扫码入口按前缀分发，不依赖网络/URL |
| **图片前端渲染、后端只存编码** | 二维码图片由前端 canvas 实时生成，后端不存图片文件，改码即时生效 |
| **打印可插拔** | 业务层只产出"码内容 + 模板数据"，打印实现层（A4 / 标签机）可替换 |
| **遵循 factory_id 多租户** | 所有反查接口 SQL 带 `factory_id`（MyBatis 拦截器自动注入，SQL 仍需写 `<if>`） |

## 3. 码体系设计

### 3.1 Payload 格式规范

```
QXX|{TYPE}|{CODE}
```

| 段 | 取值 | 说明 |
|----|------|------|
| `QXX` | 固定 | 项目前缀，防止扫到外部码误解析 |
| `TYPE` | `CARD` / `MAT` / `ROLL` / `WO` / `PKG` | 码类型 |
| `CODE` | 业务编码 | `card_code` / `batch_code` / `roll_code` / `workorder_code` / `package_code` |

**设计决策与理由**：
- 用 `|` 分隔：可读、不会出现在业务码里、解析简单（`split('|')`）。
- **不用 URL**：车间可能断网/内网，uni-app 离线解析前缀更稳，且不依赖域名配置。
- **编码业务码而非数字 id**：人可读，扫描坏了能手输；数字 id 无业务含义、跨环境会变。
- **带固定前缀 `QXX`**：扫到非本系统码（如员工私人物品条码）能识别并忽略，避免误操作。

### 3.2 码类型清单

| 类型 | TYPE | 编码的 CODE | 含义 | 引入期 |
|------|------|------------|------|--------|
| 流转卡码 | `CARD` | `card_code`（如 `CRD20260620001`） | 一批在制产品的流转载体（生产侧 + 收货动作标识） | P1 |
| 批次码（物料/成品） | `MAT` | `batch_code`（如 `BATCH20260813001`） | 一个入库批次——采购物料批次 / 生产成品批次 / 外协成品批次（仓内通用标识） | P2（采购）/ P3（生产·外协） |
| 卷料码 | `ROLL` | `roll_code`（如 `R20260813001`） | 一卷原纸（纸袋厂专用） | P2 |
| 工单码 | `WO` | `workorder_code` | 兼容旧流程/工单查询 | P1（兼容） |
| 包装/成品码 | `PKG` | `package_code` | 装箱/发货追溯 | P3 |

### 3.3 Payload 工具（后端）

新增 `QrPayloadUtil`（`com.qixiaoxia.mes.common.utils` 或 `mes.common.qrcode`）：

```java
public class QrPayloadUtil {
    private static final String PREFIX = "QXX";

    public static String build(QrPayloadType type, String code) {
        return PREFIX + "|" + type.name() + "|" + code;
    }

    /** 解析；非本系统码返回 null */
    public static QrPayload parse(String raw) {
        if (raw == null) return null;
        String[] parts = raw.split("\\|", 3);
        if (parts.length < 3 || !PREFIX.equals(parts[0])) return null;
        QrPayloadType type = QrPayloadType.from(parts[1]);
        return type == null ? null : new QrPayload(type, parts[2]);
    }
}

public enum QrPayloadType { CARD, MAT, ROLL, WO, PKG; ... }
```

集中管理格式，杜绝散落字符串拼接。

## 4. 生成时机矩阵（核心）

| 码 | 编码 | **何时生成（触发点）** | 现有触发代码 | 谁触发 |
|----|------|----------------------|-------------|--------|
| **流转卡码（CARD）** | `card_code` | **建卡即生码**（payload 派生，无需额外步骤）：①工单开工自动建卡 ②拆卡出新卡 ③手动建卡 | `ProWorkorderServiceImpl.ensureDefaultCardForWorkorder` / `ProCardServiceImpl.buildSplitCard` / `ProCardServiceImpl.insertProCard` | 后端建卡时 |
| **物料批次码（MAT）** | `batch_code` | **采购入库 confirm** 那一刻（生成物料批次） | `WmItemRecptServiceImpl.confirmItemRecpt` → `WmBatchServiceImpl.getOrGenerateBatchCode` | confirm 后打印贴货 |
| **成品批次码（MAT）** | `batch_code` | **生产入库 confirm**（`resolveLineBatch` 生成成品批次）/ **外协入库 confirm**（`resolveRecptBatch` 生成成品批次） | `WmProductRecptServiceImpl.confirmProductRecpt` / `OutsourceServiceImpl.resolveRecptBatch` | confirm 后打印贴货 |
| **卷料码（ROLL）** | `roll_code` | **原纸到货 confirm 时**（已有 roll_code，只差渲染二维码） | 收货确认流程 | confirm 后 |

> ⚠️ **修正（v2）**：原稿把批次码只挂在采购入库、并写"完工入库复用卡码不生成品码"。实际上**采购入库、生产入库、外协入库三种都会在 confirm 生成批次**（batch_code），所以三种入库 confirm 都应生成批次码(MAT)标签。"复用卡码"只对**收货动作**成立，对**成品在仓内如何标识**是漏的——成品入仓后，仓内作业（出库/发货/盘点）扫的是成品批次码(MAT)，不是卡码。

### 4.1 卡码 vs 批次码：职责对照

两种码**职责不同、服务不同角色**，不可互相替代：

| 维度 | 流转卡码（CARD） | 批次码（MAT） |
|------|-----------------|--------------|
| 编码 | `card_code` | `batch_code` |
| 何时生成 | 工单开工建卡时（最早） | 入库 confirm 生成批次时（采购/生产/外协） |
| 服务角色 | **生产工人**（报工）、**收货人**（收成品入仓） | **仓库工人**（出库/发货/盘点/库内查询） |
| 物理载体 | 流转卡（A4，随批走，完工后归档） | 物料/成品标签（贴在货上） |
| 生命周期 | 卡 COMPLETED 即终结（历史追溯用） | 货在仓期间一直有效 |
| 扫码场景 | 报工、流转查询、收货动作 | 发料/投料、出库/发货、盘点 |

**成品入库完整流程**（体现两种码的分工）：
```
末工序报工审核 → 卡 COMPLETED → 自动生成产品入库单
   │
   ▼ 收货人扫【流转卡码】（拉出对应入库单，确认数量/库位）
confirm → resolveLineBatch 生成【成品批次】batch_code
   │
   ▼ 打印【成品批次码 MAT】标签 → 贴在成品上
成品入仓
   │
   ▼ 此后仓内作业（出库/发货/盘点）扫【成品批次码 MAT】
```

### 4.2 关键洞察

1. **流转卡码 = 最早生成的生产侧码**。工单一开工就建卡、就出码、打印随批走。从此这批货每到一道工序，工人扫的都是同一张卡。
2. **批次码(MAT) 必须等 confirm**：批次身份（batch_id / material_stock）是 confirm 时才有的——收货前物料/成品还没"落库身份"，无法编码。采购/生产/外协三种入库 confirm 都生成批次，故都生成批次码。
3. **两种码各司其职**：卡码管"生产过程 + 收货动作"，批次码管"仓内流转"。成品既关联卡码（生产追溯）又带批次码（仓内标识），不冲突。

### 4.3 生成"动作"的本质

由于 payload 是 `card_code` / `batch_code` 的派生，**"生成二维码"= 业务编码已存在 + 前端按需渲染图片**。后端无需"生成码图"步骤，只需保证：
- 建卡/生成批次时业务编码已生成（现状已满足）。
- 前端能取到该编码（接口已返回 `cardCode` / `batchCode`）。

唯一需要新增的"生成侧"动作是：**入库 confirm 后触发"打印批次/卷料标签"的提示与入口**（采购物料批次码 / 生产·外协成品批次码 / 卷料码，三种均在各自 confirm 时生成）。

## 5. 扫码场景矩阵（核心）

> **端职责**：**扫码以 App 为主**（车间作业用手机/PAD）；**PC 负责码的生成、展示、打印**（管理端）。本期不给 PC 加摄像头扫码——PC 扫码（USB 扫码枪）作为可选增强，不在范围内。

| 场景 | 扫什么码 | 扫完系统干嘛（后端反查上下文） | 引入期 |
|------|---------|------------------------------|--------|
| **报工** | 流转卡码 | 卡 → 工单 → `current_process_id` 当前工序 → 可报任务 → BOM 消耗默认值 → 该卡该工序已报合格数（防超报）。**工人只填数量** | P1 |
| 流转查询（基础） | 流转卡码 | 卡状态/当前工序/工单（P1 为二维码弹窗展示基础信息；完整工序进度/报工记录查询列后续） | P1（基础） |
| 采购入库（收货动作） | 采购单码（现状，可选扫） | 按 PO 收货 → confirm 生成**物料批次** → 打**物料批次码**标签贴货 | P2 |
| 生产/外协入库（收货动作） | 流转卡码 | 扫卡拉出对应入库单 → 确认数量/库位 → confirm 生成**成品批次** → 打**成品批次码**标签贴货 | P3 |
| 仓内：发料/投料（原材料） | 物料批次码 MAT / 卷料码 | 还原 material_stock 身份 → 核销库存、写物料谱系 | P2 |
| 仓内：出库/发货（成品） | 成品批次码 MAT | 还原成品批次 → 出库核销、写发货谱系 | P3 |
| 盘点 | 批次码 MAT | 还原库位批次 → 录入实盘数 | P3 |
| 外协发货/收货 | 流转卡码 | 卡 → 工单 → 外协单；收货时卡 OUTSOURCING→ACTIVE | P3 |

> **核心区分**：**收货动作**扫流转卡码（或采购单码），把货"接进来"；**仓内作业**扫批次码(MAT)，把已经入仓的货"管起来"。同一种成品在生产端用卡码、在仓库端用批次码，两者通过 `card → workorder → batch` 关联，不冲突。

## 6. 后端设计

### 6.1 数据模型影响：零迁移（论证）

| 表 | 字段 | 影响 |
|----|------|------|
| `qxx_pro_card` | `card_code`（已有） | payload 派生，**无迁移**。`barcode_url` 字段弃用（payload 派生，不再存储） |
| `qxx_wm_batch` | `batch_code`（已有） | payload 派生，**无迁移** |
| `qxx_wm_roll_detail` | `roll_code`（已有） | payload 派生，**无迁移** |
| `qxx_wm_material_stock` | 无 barcode 字段 | 靠 `batch_code` 反查，**无字段新增** |

**结论：本期数据库零迁移**（payload 全部派生自已有业务编码）。

**可选（P3 再评估）**：若要"标签打印计数"，流转卡可复用 `qxx_wm_barcode` 表思路加 `print_count` / `last_print_time`，但 MVP 不做计数。

### 6.2 报工扫码反查接口（P1 核心）

`GET /mes/pro/card/scan/{cardCode}`
权限：`mes:pro:card:query`（复用流转卡查询权限）

**Controller**：`ProCardController.scanForReport(@PathVariable cardCode)`

**返回 `CardScanResultVO`**：
```json
{
  "code": 200,
  "data": {
    "card": {
      "cardId": 200, "cardCode": "CRD20260620001", "status": "ACTIVE",
      "currentProcessId": 5, "currentProcessName": "印刷",
      "quantityTransfered": 10000,
      "itemId": 88, "itemCode": "PB-A4-001", "itemName": "A4手提袋",
      "specification": "300×250×80", "unitName": "个"
    },
    "workorder": { "workorderId": 12, "workorderCode": "WO20260620001", "workorderName": "...", "status": "PRODUCING" },
    "currentProcess": { "processId": 5, "processCode": "PRC05", "processName": "印刷" },
    "reportableTasks": [
      { "taskId": 33, "taskCode": "TASK033", "workstationId": 7, "workstationName": "印刷机1号", "quantity": 10000, "quantityProduced": 0 }
    ],
    "consumeDefaults": [
      { "itemId": 90, "itemCode": "PAPER-300", "itemName": "300g白卡纸", "quantity": 305, "batchCode": "BATCH..." }
    ],
    "reportedQualifiedSum": 0.0,
    "canReport": true,
    "reason": null
  }
}
```

**`canReport=false` 的原因码**（`reason`）：
- `CARD_NOT_FOUND` 卡号不存在
- `CARD_COMPLETED` / `CARD_OUTSOURCING` / `CARD_SCRAPPED` 卡状态不可报工
- `WORKORDER_NOT_PRODUCING` 工单非生产中（PREPARE/PROCUDING 之外）
- `NO_REPORTABLE_TASK` 当前工序无可报任务

**校验逻辑**（Service `scanForReport`）：
1. 按 `cardCode` + `factory_id` 查卡；不存在 → `CARD_NOT_FOUND`。
2. 卡 `status != ACTIVE` → 对应原因（外协中/已完工/已报废给出明确提示，引导工人下一步）。
3. 查关联工单，`status ∉ {PREPARE, PRODUCING}` → `WORKORDER_NOT_PRODUCING`。
4. `reportableTasks`：工单下、当前工序、`PRODUCING`、非外协工位（VENDOR）的任务（复用 `feedbackEntry` 的筛选逻辑）。
5. `consumeDefaults`：复用 `ProFeedbackServiceImpl.getDefaultConsume(workorderId)`。
6. `reportedQualifiedSum`：复用 `sumAuditedQualifiedByCardAndProcess(cardId, currentProcessId)`。

**遵循项目原则**：一个接口返回报工所需全部上下文，前端零拼接、零跨域调用（体现 AGENTS.md「后端拥有数据逻辑」）。

### 6.3 批次码/卷料码反查接口（P2 物料 / P3 成品）

- `GET /mes/wm/stock/scan/{batchCode}`：按 `batch_code` + `factory_id` 还原 `material_stock`（可能多仓多行，返回列表：库位、批次、可用量、质量状态）。**物料批次码与成品批次码都是 `MAT` 类型、编码同为 `batch_code`，故同一接口通吃**——区分物料/成品由 `material_stock` 关联的 `md_item` 属性决定，不由码类型决定。
- `GET /mes/wm/roll/scan/{rollCode}`：还原卷料明细（实际规格、剩余量、状态）。

### 6.4 报工提交沿用现状

扫码只改变"识别"环节（扫卡而非选任务）。报工提交 `POST /mes/pro/feedback` 及其后端逻辑（`doInsertProFeedback` / 自动填充 / 卡推进 / 审核消费）**零改动**——`cardId` 由扫码直接带入，`resolveActiveCardId` 不再被调用（或保留作 PC fallback）。

### 6.5 编码规则核对结论（非 bug）

调研澄清：流转卡编码**不存在活动 bug**。`V40__fix_autocode_duplicates_and_missing.sql` 已补种 `PRO_CARD_CODE` 规则，而 Java（`ProWorkorderServiceImpl:690`、`ProCardServiceImpl:106`）与前端（`card/index.vue:506`）三处调用全部用 `PRO_CARD_CODE`，链路正常。`V15` 早期种子的 `CARD_CODE` 是**孤儿死数据**（无任何代码引用），无害。

**可选清理（非阻塞，可任何时候做）**：加一个迁移（下一可用版本 `V121`）删除孤儿 `CARD_CODE` 规则及其 part 行；并把手抄参考脚本 `backend/sql/seed_autocode_rules.sql:43` 的 `CARD_CODE` 改成 `PRO_CARD_CODE` 以与现实一致。**不要**改 Java/前端调用点（它们正确）。

### 7.2 App 统一扫码分发（P1）

现状：8 个页面各自调 `uni.scanCode`，无统一入口。

新增 `app/utils/scanDispatch.js`：
```js
import { parseQrPayload } from './qrPayload'

export async function scanAndDispatch(page) {
  const res = await uni.scanCode({ scanType: ['qrCode', 'barCode'] })
  const payload = parseQrPayload(res.result)
  if (!payload) {
    // 非本项目码：当作裸码，交当前页面处理（兼容手输工单号/卡号）
    return { type: 'RAW', code: res.result }
  }
  switch (payload.type) {
    case 'CARD': uni.navigateTo({ url: `/pages/mes/pro/report?cardCode=${payload.code}` }); break
    case 'MAT':  uni.navigateTo({ url: `/pages/mes/wm/issue/scan-query?batchCode=${payload.code}` }); break
    case 'ROLL': uni.navigateTo({ url: `/pages/mes/pro/slitting?rollCode=${payload.code}` }); break
    case 'WO':   uni.navigateTo({ url: `/pages/mes/pro/report?workorderCode=${payload.code}` }); break
  }
}
```

提供「扫一扫」总入口（首页/悬浮按钮），按码类型自动跳转。各业务页保留"手动输入码"兜底。

### 7.3 App 报工页改造（P1）

`app/pages/mes/pro/report.vue`：

## 8. 打印方案（可插拔，一期零硬件）

### 8.1 硬件成本参考

| 方案 | 机器成本 | 耗材 | 开发成本 | 实用性 |
|------|---------|------|---------|--------|
| 热敏/热转印标签打印机 | 轻商用 200~600 元（汉印/佳博）；工业级 1500~4000（斑马/立象） | 不干胶几分钱/张 | 中（引入 LODOP/hiprint，~1-2 周） | ⭐⭐⭐⭐⭐ |
| 普通 A4 打印机 | 0（已有） | A4 纸 | 小（复用现成 `window.print`，3-5 天） | ⭐⭐⭐ |
| 纯数字不打印 | 0 | 0 | 最小（2-3 天） | ⭐⭐ |

**决策**：硬件待定，不阻塞。设计上打印做成可插拔——一期用 A4（零成本、复用项目现成送货单/装箱单打印基建），标签打印机后续接入只换打印实现层，业务码不动。

### 8.2 可插拔打印设计（前端）

封装 `useLabelPrint` composable：
```ts
export function useLabelPrint() {
  // 一期实现：A4 window.print
  function printCard(card) { openPrintWindow('card-template', card) }
  function printMaterialLabel(batch) { openPrintWindow('material-label', batch) }
  // 预留：标签机接入点（LODOP/hiprint）
  // function printByLabelPrinter(payload, template) { ... }
  return { printCard, printMaterialLabel }
}
```

业务层只调 `printCard(card)`，底层实现（A4 / 标签机）可替换。

### 8.3 流转卡 A4 模板

复用现有 `product_sales_ship` 的 `window.print()` 模式。内容：
**卡号（大字）+ 二维码 + 产品/规格 + 流转数量 + 当前工序 + 工单号 + 工厂**——车间扫这张纸随批走即可。

## 附录 B：为什么不扫工单码 / 工序任务码（决策记录）

| 候选 | 否决理由 |
|------|---------|
| 工单码（现状） | 工单可能多卡（拆批），自动取"第一张 ACTIVE 卡"有歧义；且工单不带工序游标，仍需选任务 |
| 工序任务码 | 每道工序任务(工单+工序+工位)一张码，码量大、维护成本高；任务状态变化码就过期 |
| **流转卡码（选定）** | 一卡一批、自带 `current_process_id` 工序游标、贯穿报工→外协→分切→完工全链路；物理随批走，工人天然对应"自己这批货" |
