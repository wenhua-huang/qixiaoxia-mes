# 物料分类动态扩展属性设计

> 日期：2026-08-01
> 状态：已决策，待实施
> 前置文档：[采购订单行属性存储方案](采购订单行属性存储方案.md)（V73，已落地）

## 一、需求

1. 不同物料分类各自配置扩展属性字段，有**继承关系**（父分类配置的子类继承；通常只在大类配置）。
2. 现有纸张属性、纸袋属性是写死的（物理子表 + 固定 Vue tab），需改为分类可配置的动态扩展属性。
3. **销售订单和采购订单明细**新增/编辑时出现"扩展属性"tab 页。

## 二、产品判断：需求合理

当前实现存在结构性缺陷：

- **属性与分类脱钩**。`MdItemServiceImpl.handleSubTableInsert` 注释明确："所有分类均开放，用户自行填写"；前端 `md/item/index.vue:183-206` 的纸张/纸袋两个 tab 是**无条件渲染**，导致纸张原料也能填纸袋属性，数据无约束、界面有噪音。
- **每行业一张物理子表**（`qxx_md_item_attr_paper/paper_bag/gift_box`），新增行业需建表+实体+Mapper+Service+Vue tab，必须发版。礼品盒子表 `MdItemAttrGiftBox` 已留占位待补，印证硬编码模式已到极限。

分类驱动 + 继承是制造业标准范式（SAP 类特性、用友/金蝶自定义项、PDM 属性模板）。本质是把"写死的三张子表"收敛为"元数据驱动的动态属性"，并让销售订单行、工单对齐采购订单行已有的 JSON 方案。**结论：合理。**

## 三、与前置文档（V73）的关系与演进

| 维度 | V73（采购订单行） | 本方案（物料 + 销售行 + 工单 + 采购行） |
|------|------------------|----------------------------------------|
| 存储 | `line_attrs JSON` | 物料 `ext_attrs JSON`；销售行/工单 `line_attrs JSON`；采购行沿用 `line_attrs`（结构升级） |
| 主数据 | 仍用子表 | **升级**：物料主数据改 JSON（原方案第四节"主数据用子表"的决策被本次推翻，理由见下） |
| 结构 | 分组 `{paper,paperBag,product}` | **升级为扁平** `{attrCode:value}`（理由见下） |
| 元数据 | 无，JSON 键约定靠文档 | **落地**：原方案第八节"将来加元数据层"的 `attr_template/attr_field` 提前实现为 `attr_def/item_type_attr` |

**两处推翻原决策的理由**：

1. 主数据改 JSON：原方案主张"主数据用子表"是因为当时属性类型少且稳定。本需求要求"不同分类各自配置 + 继承 + 用户自助新增属性"，子表模式无法满足，必须元数据驱动，主数据存 JSON 值。
2. 分组→扁平：分组 `{paper,paperBag}` 是"写死行业"思想的残留——每新增行业就得加分组。扁平 `{attrCode:value}` 让属性与分类彻底解耦，任何分类配任意属性，天然契合动态 schema。采购行本次一并扁平化，消除三套结构不一致。

## 四、架构决策（已定）

- **承载方式**：JSON schema + 值（复用 `JsonMapTypeHandler`，全局已注册）
- **旧三表**（paper/paper_bag/gift_box）：**一次性迁移数据后删除**
- **结构**：**扁平 `{attrCode: value}`**
- **范围**：**一次性全做**（物料 + 销售行 + 采购行 + 工单 全链路）

### 6.3 继承机制

查询时沿 `parent_type_id` 递归 CTE 向上聚合（项目已在 `MdItemTypeMapper.xml:52` 用递归 CTE，新增"查祖先方向"）。子类重新绑定同一 attr 即覆盖（按 inherit_depth 取最近本类的 required/sort）。

> **多工厂 + FactoryIdInterceptor 关键约定（审查阻塞项 B1）**：
> `FactoryIdInterceptor` 对 SELECT 自动注入 `主表别名.factory_id`。本 CTE 主查询是 `FROM qxx_md_item_type_attr ta`，拦截器注入 `ta.factory_id=X`，**绑定关系按工厂隔离正确**。但 CTE 内部 `qxx_md_item_type WHERE item_type_id=#{typeId}` 在子查询深度>0，拦截器**不会**给它注入 factory_id——若分类树跨工厂共享（子类 parent 指向别厂根类），递归向上会泄漏别厂分类。
> 本项目分类树**工厂隔离**（V20 种子所有分类 factory_id=1，ROOT parent=0；新工厂自建独立 ROOT，不跨厂共享），正常不泄漏。但为防脏数据，**CTE 内部显式带 factory_id 条件**，不依赖拦截器：
```sql
WITH RECURSIVE ancestor_types AS (
  SELECT item_type_id, parent_type_id, 0 AS depth
    FROM qxx_md_item_type
   WHERE item_type_id = #{typeId} AND factory_id = #{factoryId}
  UNION ALL
  SELECT t.item_type_id, t.parent_type_id, a.depth+1
    FROM qxx_md_item_type t
    JOIN ancestor_types a ON t.item_type_id = a.parent_type_id
   WHERE t.factory_id = #{factoryId}
)
SELECT d.*, ta.required, ta.sort_order, a.depth AS inherit_depth
  FROM qxx_md_item_type_attr ta
  JOIN ancestor_types a ON a.item_type_id = ta.item_type_id
  JOIN qxx_md_attr_def d ON d.attr_id = ta.attr_id
 WHERE ta.factory_id = #{factoryId} AND ta.enable_flag='Y'
 ORDER BY a.depth DESC, ta.sort_order;
```
> Mapper 方法建议加 `@SkipFactoryId` 后由 SQL 内部三处 `factory_id` 自行隔离，避免拦截器二次注入破坏 CTE。实施时必须写单测覆盖：A 厂分类绑属性、B 厂同 id 分类不绑，查 A 厂 schema 不应见 B 厂属性。

## 十二、审查反馈与修订（2026-08-01 独立审查后修订）

> 本节记录经资深 MES 产品经理+架构构师独立审查后，对方案的修订。阻塞项已在正文修正（B1/B2/I1 见上文），以下为补充决策。

### 12.1 单据扩展属性的快照规则（阻塞项 B3）

**决策：单据行只快照"属性值"，不快照 schema；历史订单用当前 schema 渲染，旧 key 降级展示。**

- `line_attrs` 只存 `{attrCode: value}` 值。前端渲染单据明细时，按**当前**物料分类的 effAttrSchema 画出表单，把 line_attrs 的值填进去。
- 若 line_attrs 里有 key 不在当前 schema 中（属性后来被删/改名），这些"游离值"以**只读文本**降级展示在扩展属性 tab 末尾（label 用 attrCode），不丢数据、不报错。
- **必填校验时机**：仅在"新建/编辑保存"时校验，基于**保存时刻**该行物料分类的实时 schema；已入库的历史订单不回溯校验（历史凭证不动）。
- **物料 required 缺填处理**：编辑物料时按当前分类 schema 强校验 required；存量物料若新增了 required 属性，不阻断列表/查询，只在编辑该物料时强制补填。提供"按分类批量补录"入口（可选增强）。

### 12.2 工单 line_attrs 的内容边界（阻塞项 B4）

**决策：工单 `line_attrs` 只装"从销售行继承来的分类动态属性"，不装订单业务要求字段（productSize/printingReq/ropeSpec/packageReq/shippingReq）。**

- 这样物料/销售行/采购行/工单四处 `line_attrs`/`ext_attrs` 语义统一：都是"分类驱动的动态扩展属性"。
- 工单的 5 个订单业务要求字段**保留平铺列不动**（与销售行对称，销售行也保留平铺列）。即：**工单表 qxx_pro_workorder 的 product_size/printing_req/rope_spec/package_req/shipping_req 列不删、ProWorkorder 实体这些字段不删**，只**新增** `line_attrs JSON` 列承载分类动态属性。
- 相应地：第 5 阶段"工单删平铺规格列"**取消**；`buildWorkorderFromLine` 的 5 行硬拷贝**保留**（仍拷业务要求字段），**新增**一行 `wo.setLineAttrs(line.getLineAttrs())` 拷分类动态属性；`createSkuVariantForWorkorder` 读 `getProductSize` 等**保留**，无需改。
- **第 1 阶段 V90 修正**：工单迁移改为只 ADD `line_attrs` 列（V89 已做）、**不迁不删平铺列**。V90 仅做：采购行扁平化 + DROP 旧三子表。

### 12.4 缓存与索引（重要建议 I2）

- **缓存**：effAttrSchema 是低频写高频读。用 Caffeine 本地缓存，key=`factoryId:typeId`，TTL 30 分钟；`item_type_attr` 增删改时主动 evict 该 factoryId 下所有 typeId（或简单全清）。
- **索引**：`item_type_attr(factory_id, item_type_id)`、`item_type_attr(attr_id)`、`attr_def(attr_code)`、`qxx_md_item_type(parent_type_id)`。JSON 列暂不加函数索引（采购行明确不按属性过滤）。

### 12.5 权限拆分（重要建议 I3）

属性配置是高风险操作（误改污染全厂物料展示）。`/md/attrDef`（属性字典 CRUD）和 `/md/itemType/attrBind`（分类绑定）必须是**独立菜单**，默认只授工厂管理员/系统管理员角色；普通物料员/销售/采购只有读权限（通过物料页/订单页间接读 schema）。
